# debug-crash-handler

## 2026-08-20 — 🐛 Fix Windows crash dump attribution, remove dead crash.log flow

Reworked the Windows minidump crash handler in `nel/src/misc/debug.cpp`. A prior change had introduced a hand-rolled dedicated dump-writing thread (to avoid running Breakpad's `WriteMinidump()` on the potentially-corrupted crashed thread's stack), but it discarded the real `EXCEPTION_POINTERS*` and crashed thread ID, so every generated minidump self-attributed the crash to whichever thread happened to call `WriteMinidump()` (the dump thread itself) instead of the thread that actually faulted.

Investigation against the exact Breakpad source used by the client build docker (commit `b988fa74ec18de6214b18f723e48331d9a7802ae`) showed Breakpad already implements this exact dedicated-handler-thread pattern internally via `ExceptionHandler::WriteMinidumpForException()`, correctly capturing the requesting thread ID on the crashed thread before handing off. Replaced the hand-rolled `DumpRequestEvent`/`DumpDoneEvent`/`DumpMiniDumpThreadProc`/`ensureDumpMiniDumpThread()` machinery with a persistent `google_breakpad::ExceptionHandler *DumpHandler` (`HANDLER_NONE`, so our own `_set_se_translator`/`EDebug` flow stays the primary crash detection path); `DumpMiniDump()` and the new process-wide `unhandledExceptionFilter()` (installed via `SetUnhandledExceptionFilter`, last-resort catch for faults on threads with no SE translator, such as a raw `CreateThread()`'d thread) now call `DumpHandler->WriteMinidumpForException(excpInfo)` with the real exception pointers.

Also fixed a regression introduced during that rework: `ensureDumpHandler()` baked in `getLogDirectory()` at startup time, before any later `changeLogDirectory()` call (e.g. from a `-logsdir` argument), so the persistent handler's dump path could go stale while `crash.log` (written separately by `report()`, recomputed fresh each time) stayed correct — silently causing no `.dmp` to be produced at all. Added `refreshDumpHandlerPath()`, called right before every `WriteMinidumpForException()`, to recompute the path each time.

Added a `crashtestreal` debug command (`nel`, always available even in `FINAL_VERSION`) alongside the existing `crashtest`: it faults on a freshly created thread with no SE translator installed, so the fault reaches the client entirely outside any command/Lua call stack — unlike `crashtest`, whose `EDebug` exception gets silently swallowed by `ICommand::execute()`'s own `catch(const exception&)` when triggered via a chat command. Removed `crashtestdump`/`TestForceFaultInDumpMiniDump` (it tested a fault in the now-removed hand-rolled dump thread; no longer meaningful since dump writing is Breakpad's own internal thread).

Separately, removed dead Windows-only code in `EDebug::createWhat()`: the `report(...)`/`crash.log`/`NL_CRASH_DUMP_FILE` call and the `addStackAndLogToReason()` function. On Windows, `addStackAndLogToReason()`'s body was empty, and its `#elif !defined(NL_OS_MAC)` backtrace branch was unreachable code that didn't even compile on its own (referenced an undeclared variable) — proof it never ran on this platform. The `report()` call was meant to launch `crash_report.exe`, a companion tool that hasn't shipped in about 15 years. Left `nel/src/misc/report.cpp`, `nel/src/misc/displayer.cpp` (separate assert/warning dialog flow, still calls `report()`), and the `nel/tools/misc/crash_report`/`web/public_php/crash_report` tool untouched, since they may still be relevant on other platforms.
