## 2026-09-03 — Add macOS universal2 build scripts (environment setup + externals + client)

Added a native macOS build pipeline under `macosx-build/` to compile the Ryzom client as a universal2 (x86_64 + arm64) binary, targeting macOS 11.0. Three scripts, meant to be run directly on a Mac (no Docker, no CI dependency):

- `setup-environment.sh` — one-time toolchain setup: checks/installs Xcode Command Line Tools (triggers the normal GUI installer if missing), Rosetta 2 (Apple Silicon only, needed to run x86_64 autotools test binaries during third-party builds), a dedicated CMake 4.4.3 (Kitware's official universal2 build, since a modern Xcode requires a recent CMake for its Xcode-generator compiler detection to work), and xcbeautify (official universal2 build, used to make `xcodebuild` output readable).
- `build-externals.sh` — compiles every third-party dependency from source as universal2 static libs into `macosx-build/external/`: zlib, libxml2, libpng, OpenSSL, CURL, Lua 5.3, Boost (headers only), Luabind (nimetu fork), FreeType, libjpeg-turbo, giflib, libogg, libvorbis, Google Breakpad. Mirrors the dependency list/versions already used by `ryzom-docker`'s Linux/Windows Dockerfiles. Skips libraries already built (marker files under `external/.built/`), so it's safe to re-run.
- `build.sh` — main entry point: verifies the environment, calls `build-externals.sh` if needed, configures and builds `ryzom_client` itself via the Xcode CMake generator, producing `Ryzom.app`. Takes an optional `fv`/`steam` argument for the client build type (defaults to `fv`); the `steam` type requires `STEAM_DIR` pointing at a local Steamworks SDK checkout (proprietary, can't be fetched automatically).

### Deployment target strategy

Xcode 16+ dropped support for targeting below macOS 11.0 entirely (even for the x86_64 slice), so a recent Mac can only produce a universal2 binary floored at 11.0. To still support older Intel Macs down to 10.8/10.9 (matching `ryztart`'s own floor), the plan is: build on a recent Mac (11.0, both slices) for the future-proof build, keep the existing older VM (still on an old Xcode) for a legacy x86_64-only 10.8 build, and merge the two via `lipo`/`llvm-lipo` from a Linux machine (the executables are fully static, so no relinking is needed — just merging two already-linked Mach-O slices). This split isn't needed for the Steam build variant: verified via the app-specific Steamworks Hardware Survey that no Ryzom players are on macOS below 12, so Steam builds stay universal2-11.0-only, produced directly by `build.sh` on the recent Mac.

### Bugs and quirks found during the first real build (macOS 15.7.2 Intel, Xcode 26.1.1, CMake 4.4.3)

- MacPorts (present on the test machine) shadows almost everything — its `pkg-config`, and libraries like an ancient OpenSSL 1.0.2 — ahead of our own builds. `CMAKE_SYSTEM_IGNORE_PATH` alone isn't reliable (doesn't stop some CMake modules' internal probes, e.g. `FindOpenSSL.cmake`); `PKG_CONFIG_LIBDIR`/`PKG_CONFIG_PATH` must also be emptied, and each dependency needs explicit `-D<LIB>_INCLUDE_DIR`/`-D<LIB>_LIBRARY` hints rather than relying on auto-detection.
- ryzom-core ships several custom `Find*.cmake` modules with non-standard variable names: `FindIconv.cmake` expects `ICONV_INCLUDE_DIR`/`ICONV_LIBRARIES` (not the stock `Iconv_*`), and `FindOgg.cmake`/`FindVorbis.cmake`/`FindLuabind.cmake` use a shared `FIND_PACKAGE_HELPER` macro that only looks at a `<NAME>_DIR` variable (`OGG_DIR`, `VORBIS_DIR`, `VORBISFILE_DIR`, `LUABIND_DIR`) for its library search — it explicitly passes `NO_CMAKE_SYSTEM_PATH`, so `CMAKE_PREFIX_PATH`/`CMAKE_SYSTEM_IGNORE_PATH` have no effect on it.
- libjpeg-turbo's own `CMakeLists.txt` unconditionally refuses more than one value in `CMAKE_OSX_ARCHITECTURES` ("contains assembly code"), before `WITH_SIMD` is even read — built once per architecture and merged with `lipo` instead, like OpenSSL/Breakpad.
- libpng's `-DPNG_ARM_NEON=off` CMake option stopped being effective after upgrading to CMake 4.4.3 (its `TARGET_ARCH` detection behaves differently than the older `CMAKE_SYSTEM_PROCESSOR`-based check). The actual fix is forcing the `PNG_ARM_NEON_OPT=0` preprocessor macro directly via `CMAKE_C_FLAGS`/`CMAKE_CXX_FLAGS`, which `pngpriv.h` honors regardless of what CMake's own option resolves to.
- Apple's SDK ships its own (older, `#include <zlib.h>`-visible) `zlib.h`, which wins over our `-isystem`-added include path — fixed by injecting our own zlib include path as a plain `-I` (higher priority) via `CMAKE_C_FLAGS`/`CMAKE_CXX_FLAGS`.
- CMake 4.x removed support for `cmake_minimum_required(VERSION 2.6)` (used by ryzom-core itself and some of its dependencies like Luabind) — worked around with `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`, without touching any third-party `CMakeLists.txt`.
- Modern macOS (SIP + dyld shared cache) no longer ships system libraries as real `.dylib` files on disk — linking against `libiconv` needs the active SDK's `.tbd` stub instead, resolved dynamically via `xcrun --sdk macosx --show-sdk-path`.
- `WITH_STATIC` defaults to `OFF` on macOS (`ON` only on Windows) in `nel.cmake` — some conditional links (e.g. libogg in `nel/src/sound/CMakeLists.txt`) are gated behind `IF(WITH_STATIC)`; since this whole pipeline links everything statically, `-DWITH_STATIC=ON` is required explicitly.
- Xcode 15+'s "User Script Sandboxing" blocks CMake-generated `CMake PostBuild Rules` scripts (file access outside declared paths) — disabled via `-DCMAKE_XCODE_ATTRIBUTE_ENABLE_USER_SCRIPT_SANDBOXING=NO`.
- Found and fixed two real upstream bugs in `ryzom/client/src/CMakeLists.txt` (not build-script workarounds — worth upstreaming): `RYZOM_OUTPUT_DIR` and the `ryzom_client_patcher` copy step both hard-coded `${CMAKE_RUNTIME_OUTPUT_DIRECTORY}`, which only resolves correctly for single-config generators (Makefiles/Ninja, used on Linux/Windows) — never exercised against the Xcode generator (multi-config, adds a `Release/` subdirectory) before. Replaced with the generator expressions `$<TARGET_BUNDLE_DIR:ryzom_client>` and `$<TARGET_FILE:ryzom_client_patcher>`, which resolve correctly regardless of generator.
- `xcbeautify` only reformats output lines it recognizes and silently drops anything it doesn't — in a parallel build (`-jobs N`) this can hide the actual compiler error behind a wall of unrelated output. `build.sh` now `tee`s the full untouched `xcodebuild` output to `${BUILD_DIR}/build.log` before piping it through `xcbeautify`, and on failure dumps the log's last 100 lines (plus its full path) to stderr under a `LAST BUILD LINES` banner, regardless of what `xcbeautify` chose to show.
- A full line-by-line comparison against `ryzom-docker`'s `client_linux`/`client_windows` CMake invocations turned up two missing variables relevant to macOS: `-DDESCRIBE="..."` (branch/revision/commit version string shown in-game, computed the same way as the other two platforms) and, far more importantly, `-DWITH_STATIC_DRIVERS=ON`. Without it, `NL_TARGET_DRIVER` (`CMakeModules/nel.cmake`) builds the OpenGL/OpenAL drivers as loadable `MODULE` bundles instead of static libs, and `nel/CMakeLists.txt` never defines `NL_STATIC` — so `nel/src/3d/dru.cpp` (and the equivalent sound driver code) falls into its `dlopen`/`loadLibrary` runtime-loading branch instead of calling the driver's `createXxxDriverInstance()` directly. Since nothing in this pipeline bundles those driver modules into `Ryzom.app` (unlike the Linux script's explicit `ldd`-based `.so` bundling step), the built client would have thrown `EDruOpenglDriverNotFound()` at startup. `-DWITH_STATIC_DRIVERS=ON` makes the drivers link statically into the executable, matching the "fully static, no external modules" assumption the whole pipeline (including the planned `lipo` assembly) already relies on.
- `-Wno-everything` alone didn't fully silence warnings (e.g. `-Wdeprecated-declarations` on `sprintf` in `mem_stream.h` kept showing) — being a normal `-W*` flag, it's order-sensitive, and Xcode's own default `CLANG_WARN_*` build settings can re-enable specific warnings after it in the generated invocation. Added `-DCMAKE_XCODE_ATTRIBUTE_GCC_WARN_INHIBIT_ALL_WARNINGS=YES`, which maps to the unconditional `-w` switch (disables clang's diagnostics engine outright, not order-sensitive).
